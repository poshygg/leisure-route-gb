# 설계 결정 기록 (ADR)

## ADR-001 — 라우팅 엔진을 쓰지 않고 직접 구현한다

**결정**: `igraph` / `rustworkx` 로 직접 Dijkstra. Valhalla·GraphHopper를 라우팅에 쓰지 않는다.

**근거 (검증됨)**
- **Valhalla**: costing이 Valhalla 자체 정규화 속성에만 작동. `use_hills`·`step_penalty`·
  `walkway_factor` 등은 축 D(보행편의) 하나만 커버. `exclude_polygons`는 **회피만 되고 선호 불가**.
  임의 속성 주입은 C++ 포크 필요.
- **GraphHopper**: custom model DSL(`if`/`else_if` + `multiply_by`/`limit_to`)은 우리가 원하는 형태.
  그런데 임의 OSM 태그를 encoded value로 올리는 건 **공식 답변이 "소스 수정 필수"**.
  `areas`(GeoJSON)는 **불리언 멤버십(`in_<id>`)만** 주고 연속값이 안 됨.
- 그래프가 작다: 시군당 수만~십수만 엣지. 100만 엣지에서도 Dijkstra 수십~수백 ms.
- **비용 함수가 곧 제품**이라 외부 DSL에 위탁할 이유가 없다.
- 학습 루프가 라우팅을 수천 번 호출한다 (앵커 × λ 스윕). HTTP 왕복이면 안 된다.

**포기하는 것**: turn restriction, contraction hierarchies, 등시선, 폴리라인 인코딩. v1에서 불필요.

**Valhalla를 쓰는 유일한 곳**: 두루누비 GPX 맵매칭 (`trace_attributes` → `edge.way_id`).

**운영 전환 시**: GraphHopper + 제네릭 `EncodedValue` 파서 하나
(`RoadClassLink.java` / `OSMRoadClassLinkParser.java` / `DefaultImportRegistry.java` 를 청사진으로,
`gh:score:*` 패턴 태그를 일괄 매핑). 클래스 하나로 15개 특징 커버.

**하지 말 것**: PBF 태그 위장(`highway=footway`로 바꿔치기), Valhalla traffic tile로 speed 조작
(ETA가 거짓말이 됨).

## ADR-002 — λ는 이분 탐색이 아니라 격자 스윕

**결정**: `λ ∈ linspace(0, 8, 24)` 전수 스윕 후 예산 만족하는 것 중 amenity 최대 선택.

**근거**: λ → 우회율이 **엄밀히 단조가 아니다.** 이분 탐색은 틀린 답을 낼 수 있다.
24점 스윕이면 Dijkstra 24회 = 여전히 수백 ms이고, **최단/균형/여유 3옵션을 같은 스윕에서 공짜로** 얻는다.

## ADR-003 — 비용은 나눗셈 형태

**결정**: `cost(e) = length(e) / (1 + λ·A(e))`

**근거**: `length·(1-λA)` 는 음수가 될 수 있고 Dijkstra는 음수 가중치에서 깨진다.
나눗셈은 항상 양수이고 해석도 자연스럽다 — `A=1, λ=1` → "이 길 1m는 0.5m처럼 느껴진다".

## ADR-004 — 특징은 테이블, 축 추가는 행 추가

**결정**: 특징 정의를 `config/features.csv` 에 두고 코드에 하드코딩하지 않는다.

**근거**: 축 C~F를 나중에 켤 때 코드 변경 없이 행만 추가하면 되게 한다.
계산 방식이 4개(`area_ratio`, `count_weighted`, `proximity`, `presence`)뿐이라
축 A·B·Z 전체가 함수 4개로 끝난다. 축 C~F는 새 함수가 필요해서 v1에서 뺐다.

## ADR-005 — 계산층(연속값)과 표시층(명사 라벨)을 분리한다

**결정**: 내부는 연속값, 사용자에게는 임계값으로 유도한 명사 라벨.

**근거**
1. **변별력** — 이진 라벨이면 해파랑길 수십 구간이 동점이 되어 순위가 안 매겨진다
2. **임계값을 정하려면 분포가 먼저 있어야 한다** — 이진화는 그 다음 단계다
3. **뷰포인트** — 국소 최댓값 지점을 찾아야 하는데 "있음/없음"만으로는 어디 찍을지 모른다

원본 데이터가 이미 명사다 (임상도 `임상` = "활엽수림"). 면적비는 그 명사를 **구간에 배분하는
과정의 중간값**이고, 최종 출력은 다시 명사다. 명사 → 면적비 → 명사.

## ADR-006 — 앵커는 특징에 절대 넣지 않는다

**결정**: 명승 · 지질명소 · 도립·군립공원 · 국가숲길은 검증 전용.

**근거**: 앵커를 특징으로 쓰면 AUC가 무의미해진다. 국가유산 데이터는 **종목코드로 명승을
먼저 분리**해서 앵커 파일 / 특징 파일로 나눈다.

**추가 위험**: 두루누비도 앵커인데, 노선이 문화재를 지나가도록 설계됐으면 B1이 앵커 정보를
일부 담는다. 완전 분리가 불가능하므로:
- 학습은 두루누비 / 검증은 명승·공원으로 **앵커 두 벌 분리**, 또는
- **지역 홀드아웃** (경주 학습 → 영덕 검증)

## ADR-007 — 뷰포인트에 보상을 놓는다

**결정**: 엣지 보상 대신 뷰포인트(점) 보상.

**근거**: 문제 유형이 Arc Orienteering → **(Node) Orienteering** 으로 바뀐다.
후자가 표준적이고 탐욕 삽입이 "다음에 어느 뷰포인트를 넣을까"로 단순해진다.

- 이미 점인 것 (B1~B3, B5): 그대로 사용
- 면·선인 것 (A1~A4, A6): 50m 소구간의 **국소 최댓값** 지점에 찍기

## ADR-008 — 손 라벨링을 하지 않는다

**결정**: 구간 라벨은 전부 임계값으로 유도. 사람이 붙이는 라벨링 작업 없음.

**근거**
- 속성 라벨("이 폴리곤은 활엽수림")은 **이미 공공데이터에 있다** (임상도 `임상`,
  토지피복 세분류 코드, 국가유산 유형분류, 조형물 `작품유형`)
- 손 라벨링은 재현 불가하고, **임계값 바꿀 때마다 전부 다시** 해야 한다

**사람이 판단하는 유일한 것**: 임계값 8~9개 (`config/display_rules.csv`),
그리고 라벨 문구 카피라이팅.
